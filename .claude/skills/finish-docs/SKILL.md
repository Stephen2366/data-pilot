# Module Finish · Docs（技术档案与复盘写作）

本 skill 是模块收工整理的**后半程**，负责基于固化素材写三份文档：**AI_CONTEXT_CHANGELOG 模块档案、AI_CONTEXT 最新事实摘要、dev-log 学习复盘**。

```text
finish-module（注释查漏 + 验证 + 素材固化到 <module>-notes.md）
        ↓
finish-docs（本 skill：技术档案与复盘写作）
        ↓
用户人工审查
        ↓
accept-module（最终门禁检查）
```

## 核心原则

过程细节未记录就不编；档案编写信息来源：

- `docs/notes/<module>-notes.md`（**首选**，前半程固化的素材）
- 会话记忆（开发和收工是同一个会话时可用）
- `docs/state/AI_CONTEXT.md`
- `docs/state/AI_CONTEXT_CHANGELOG.md`
- git diff
- 终端验证输出

素材缺失时如实说明：AI 档案里写"过程细节未记录"；dev-log 里写"此处素材未记录，待补充"（或留空后续补记），不自行编造。

验证快照必须来自 notes.md 固化的真实命令输出，或当前对话中明确可见的真实命令输出。不能写“预计通过”“应该通过”。

## 阶段 1：读取素材

1. 读取 `docs/notes/<module>-notes.md`——**必读**，包含：改动文件清单、关键决策与取舍（含选项/风险/推荐/用户选择）、注释小结、验证快照、参考资料、遗留。
2. 读取 `docs/state/AI_CONTEXT.md` 当前状态 / 最新事实快照，确认当前模块、默认配置、最新基线。
3. 按需读取 `docs/state/AI_CONTEXT_CHANGELOG.md` 近期变更记录，确认档案格式与最近结论。
4. 跑 `git status --short` 和 `git diff --name-only` 核对改动范围与 notes.md 一致。
5. 如果 notes.md 缺失关键素材（例如没有验证快照、没有决策记录），在文档里明确写“过程细节未记录”，并提示用户：可以补跑验证/补记素材后再继续；不要自行脑补。

## 阶段 2：更新 docs/state/AI_CONTEXT.md / docs/state/AI_CONTEXT_CHANGELOG.md

模块完成时，在 `docs/state/AI_CONTEXT_CHANGELOG.md`「变更记录」头部新增一节（`###` 标题），保存完整模块档案和实验记录。

同时只把会影响续接判断的最新事实摘要同步到 `docs/state/AI_CONTEXT.md`，例如当前模块、默认配置、最新评测基线、重要实验结论或活跃坑。`docs/state/AI_CONTEXT.md` 必须保持短小，不再承载完整历史变更记录。

「变更记录」模板：

```md
### Mx 模块名（YYYY-MM-DD）

- 改动范围：先跑 `git diff --name-only <base>..HEAD`（base 为本模块起始 commit）获取完整变更清单，再归并为 glob 模式（如 `engine/nl2sql/*`、`app/schemas/agent.py`），归并后逐条对照原始清单确认无遗漏。如果无明确起始 commit，用 `git status --short` 和 `git diff --stat --cached` 代替。
- 关键记录：
  - 比如关键决策、决策原因、实验结果、新发现、用户做出的选择
- 参考资料：
  - 查了什么，借鉴了什么，没照搬什么；如果未查阅，写“无”
- 验证快照：
  - pytest：结果
  - alembic / seed / API / eval：结果
  - warning：是否影响
- 遗留/后续：
  - 比如：下一模块要接什么，当前还有什么风险，后续采用什么技术或方法
```

同时更新 `docs/state/AI_CONTEXT.md` 顶部「当前状态」：「上一模块验收」在收工时填「Mx 未验收（待 accept-module）」（Mx = 本次收工的模块）；验收通过后由 accept-module 改写，本 skill 不代填「已验收」。

如果只是小修复，不写完整档案，只在 `docs/state/AI_CONTEXT_CHANGELOG.md`「变更记录」新增一个 `###` 条目（内容 1-3 行）；仅当它影响当前路线时，再同步一句到 `docs/state/AI_CONTEXT.md`「最新事实快照」。

新结论推翻或修正旧条目判断时（如归因修正、实验结论反转、口径变化），除了写新条目，还要在原条目处加一行 ⚠️ 注 指向新结论——让读旧条目的人当场看到它已过时，防止错误判断被后续误读。

## 阶段 3：更新 dev-log.md（最重要的阶段）

只有模块完成时在 `docs/dev-log.md` 末尾追加新的模块记录，小修复则不更新。本文档给用户读，新手友好，不给 AI 堆上下文。不写没实现的能力。

模块记录的各个小节都要用 `**...**` 加粗标出关键词、核心决策、类比锚点、量化成果和面试 talking point 等。加粗服务于一眼抓重点，新手扫读友好，不要整句加粗。

按照以下模板的要求写：

````md
## ★ Mx 模块名（★ 数量：★ ★：重要任务章节，需要好好理解、面试有得聊的模块；★：一般任务章节，面试复盘时快速过一遍就行的模块）
````

### 「代码阅读路线」写作细则

「代码阅读路线」必须回答：从哪里开始读、每一步看什么、这些文件如何协作。每个编号项默认包含以下信息；短小文件、纯报告文件等可合并说明，避免为凑规则写成长段。

- 从哪个入口开始读；如果这一步是流程代码，说明它接收什么、产出什么；如果是配置 / 报告 / 文档，说明它被谁消费、解决什么问题。
- 点名这一段的关键设计，并用 1-2 句解释它解决了什么问题、为什么这样放在这里。
- 不要只写“重点理解 XXX”，要让用户不用精读代码就能知道这部分的相关信息。
- 如果有容易分散注意力的细节，说明哪些实现细节可以先跳过。

根据文件长度或作用控制单项长度。优先使用 **加粗关键词** 标出阅读锚点。面向新手学习和理解，避免写成冗长的函数说明；如果一个文件承担多步流程，用“先看...然后看...最后看...”组织。以下是2个较长的文件的示例：

```
2. **评测执行**：`eval/run_eval.py`
   可以按“一条 case 的旅程”来读：先看 `main()`，它负责串起参数、用例、执行和报告。然后看 `load_cases()` 如何把 YAML 变成 `EvalCase`；`seeded_api_client()` 如何用 **内存 SQLite + dependency override** 复用真实 API；`run_cases()` 如何调用 `/api/query`；最后 `write_report()` 如何生成 Markdown 报告。重点理解这里验证的是 **API seam**，不是内部函数；这样能同时检查 API 契约、Trace、图表字段和安全拦截，不会因为绕过路由而漏掉真实调用链问题。
   
3. **Seed 数据工厂**：`scripts/seed_data.py`
主角是 `seed_database()` 和 `verify_business_facts()`。前者按父表、事实表、桥接表、宽表的顺序生成数据；后者用真实 SQL 查固定事实。读的时候重点看：外键靠 ORM 对象关系，不靠自增 ID；固定事实靠 `sku/coupon_code/channel_code` 等业务键，不靠 `id=1`。
```

### 「面试怎么讲」写作细则

```
追问难度分层：

- [基础追问]：用于训练用户把模块讲清楚。问题可以问模块目标、核心概念、主流程，但不能只是纯概念定义，也不能是送分题。回答要体现用户真的理解这个模块，而不是背名词。
- [工程/深挖追问]：用于训练真实工程判断，问题必须带一点压力。问题可以追问设计取舍、失败场景、降级策略、数据边界、安全边界、评测口径、可维护性、扩展性、技术债、后续路线等。回答要能落到本模块的代码、验证、风险和取舍上。
- [压力追问]：用于模拟资深面试官的一针见血式质疑。问题可以带有不完全友好的预设，也可以没有标准答案，重点训练用户如何承认边界、澄清目标、给出证据、说明取舍，并把问题拉回本模块真实工程价值。不要为了展示模块优点而设计问题；这类问题应该让回答者感觉“有点难接”。

数量要求：

- 追问数量根据模块范围、复杂度和面试价值灵活调整。
- 小模块可以只写 1 个基础追问 + 1 个工程/深挖追问，不为了凑数量强行写问题；关键模块可以增加 `工程/深挖追问` 或 `压力追问`，覆盖关键点和可能的弱点。
- 涉及架构、数据库、安全策略、评测体系、可观测性、长期路线，或者存在明显争议点 / 不完美结论 / “是不是过度设计”质疑空间的模块，优先增加 `压力追问`。

问题优先覆盖：

- **设计取舍**：为什么这个复杂度值得加？有没有更简单方案？为什么没选？
- **失败场景**：如果这个模块误判、超时、不可用、召回漏掉、写入失败，会怎样？
- **验证证据**：你怎么证明它有效？看了哪些测试、指标、trace、eval 或 smoke？
- **扩展边界**：数据量、业务复杂度、Agent 步骤变多后怎么演进？
- **技术债**：当前哪些地方是刻意没做的？为什么现在不做？
- **口径一致性**：本地报告、trace、LangFuse、eval 之间如何避免各说各话？

禁止写低价值问题：

- 不写“X 是不是必须的？”这种答案显然是否定的问题。
- 不写“为什么不用 X？”但回答只是复述当前方案优点的问题。
- 不写纯概念定义题，例如“什么是 TraceRouter？”
- 不写问题里已经暗示答案的提问，例如“为什么你选择了更稳定的方案？”
- 不为了凑数量强行写问题。
- 不把模块优点包装成面试官提问。
- 压力追问可以尖锐，但不能胡搅蛮缠；问题应基于本模块第一段叙述、真实边界或明显争议点提出，而不是凭空否定项目。

对于[压力追问]，回答时不要硬装完美。推荐顺序：

1. 先承认对方质疑里合理的部分。
2. 再澄清本模块的真实目标和边界。
3. 然后给出已经验证过的证据。
4. 最后说明如果进入下一阶段，会怎么补齐。

压力追问举例（`→` 表示回答完前一个问题后紧接着的追问）：

- “你这个 Agent 到底解决了什么现有方案没解决的问题？”
- “你怎么保证上下文不超限？超了怎么办？” → “上限多少？你实测过没？”
- “你说压缩了 82% token，怎么算的？基线是什么？” → “你说你只在小PR上跑过，那如果 PR 改 20 个文件呢？”
- “你的 code review 项目遇到低风险改动直接跳过大模型，怎么判断？” → “ A=1 改成 A = 1 语法树变不变？” → “那 A=1 改成 A=2 呢？”
- “你科研项目里的多 Agent 协作，信息传递怎么保证不丢失？” → “那内容语义呢？上一个 Agent 的推理过程怎么传给下一个？”
- “AI云硬件对延迟和稳定性要求高很多，你在这方面有没有经验？”
- “有没有量化指标、日志埋点？”
- “那如果场景变了呢？” → “还有呢？” → “有什么问题？”
- “你这部分做了挺多工作但业务能力没有明显提升，这是不是偏工程自嗨？”
```
