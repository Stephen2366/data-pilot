# Module Finish（模块收工整理）

用于模块代码开发完成后的“收工整理”。它不是最终验收门禁；最终验收由 `accept-module` skill 负责。

## 核心原则

过程细节未记录就不编。

如果从以下来源都找不到某个决策、踩坑或命令信息：

- 当前对话
- `docs/AI_CONTEXT.md`
- `docs/AI_CONTEXT_CHANGELOG.md`
- `.agent_work/temp/<module>-notes.md`
- git diff
- 终端验证输出

那就在日志里写“过程细节未记录”，不要脑补合理故事。

验证快照必须来自本 skill 实际跑过的命令，或来自当前对话中明确可见的真实命令输出。不能写“预计通过”“应该通过”。

## 与 accept-module 的关系

```text
finish-module
  负责：补注释 + 跑验证 + 写技术档案 + 写学习复盘
        ↓
用户人工看一遍，可要求小修
        ↓
accept-module
  负责：最终门禁检查
```

两个 skill 独立调用，不互相嵌套。收工完成后，提示用户可以继续调用 `accept-module` 做最终验收。

## 阶段 0：确认范围和素材

1. 读取：
   - `AGENTS.md` 或 `CLAUDE.md`
   - `docs/AI_CONTEXT.md`
   - 当前阶段计划文件
   - 当前模块小节

2. 确认模块范围：
   - 当前模块名称
   - 当前模块验收标准
   - 不属于本模块的内容不要补做

3. 收集改动范围：
   - 优先使用用户提供的模块起始 commit
   - 如果没有 commit，使用 `git status --short` 和 `git diff --stat`
   - 只处理本模块相关文件，不回滚用户改动

4. 收集过程素材：
   - 读取 `docs/AI_CONTEXT.md` 当前状态 / 最新事实快照
   - 按需读取 `docs/AI_CONTEXT_CHANGELOG.md` 近期变更记录
   - 读取 `.agent_work/temp/<module>-notes.md`，如果存在
   - 查找当前对话中已经跑过的验证命令输出
   - 如果模块中曾向用户确认关键取舍，必须记录当时给出的选项、主要风险、推荐方案和用户最终选择；不要只写最终结论
   - 如果素材缺失，后续日志中明确写“过程细节未记录”

## 阶段 1：注释查漏补缺

目标：把本模块代码的注释从"开发时顺手写的"提升到"复盘时能读懂的"。分 4 遍扫描，每遍独立关注点。

### 前置：确定文件范围

1. 获取本模块变更清单：
   - 如果用户提供了模块起始 commit，跑 `git diff --name-only <base>..HEAD`。
   - 如果用户没有提供模块起始 commit，使用 `git status --short`、`git diff --name-only` 和 `git diff --name-only --cached` 获取当前工作树变更。
   - 如果模块已经部分提交，再结合 `git log --oneline` 和当前模块范围判断。
   - 不确定时不要乱猜，只说明“未提供模块起始 commit，本次按当前工作树变更检查”。

2. 按计数口径剔除豁免项，得到**需检查文件清单**。豁免只适用于无业务逻辑或自解释的结构：空 `__init__.py`、纯 re-export、纯字段模型、只做简单赋值的 `__init__`、明显局部且自解释的内部闭包。若 `__init__` / 闭包包含分支、资源管理、外部依赖、关键状态初始化，则不能豁免。纯字段模型只有在类级 docstring 已解释职责、字段含义已通过命名 / `Field` / 注释足够清楚时，才允许不逐字段补注释。
3. 清单中的文件必须全量检查，不抽样；不属于本模块的用户改动不要顺手重写。

### 第 1 遍：覆盖扫描 —— 有没有

对清单中每个文件，逐个列出模块级 docstring、每个类、每个函数/方法（不含豁免项），标记状态：

| 状态 | 含义                                                         |
| ---- | ------------------------------------------------------------ |
| ✅    | 有 docstring 或开头行内注释                                  |
| ❌    | 完全没有任何解释                                             |
| ⏭️    | 豁免（pytest 函数有自描述名+开头注释、常量子类、纯字段模型等） |

- **所有 ❌ 项必须当场补写注释**，补完后把状态改为 ✅。
- 补写时遵循 CLAUDE.md 或 AGENTS.md 的「代码风格」。
- 产出：一句话结论，如 `23 个类/函数，23 已覆盖（含补写 3 个），0 缺失`。

### 第 2 遍：质量扫描 —— 够不够深

这一遍只关注注释的**内容深度**，不关注格式。从本模块代码中挑出：

- **每个新概念**（本模块第一次出现的术语、技术、模式）：
  - 用通俗语言解释了吗？一个没学过这个概念的读者能看懂吗？必要时有没有类比？
  - 如果没有，补写到"能懂"为止。
- **1-3 个关键设计决策**（模块最重要的架构选择）：
    - 模块很小时，至少说明 1 个最重要的取舍。
    - 模块较大时，优先选影响数据库、架构分层、安全策略、评测结构、响应契约的决策。
    - 相关注释是否解释了“为什么这样做”？
    - 如果有明显替代方案，是否解释了“为什么不用另一个方案”？
    - 如果只写了“做什么”没写“为什么”，补写理由。

- 产出：列出检查了哪些新概念、哪些设计决策，各自补了什么；如果已足够，也写明“已足够”。

### 第 3 遍：可读性扫描 —— 函数内部好不好读

这一遍只看函数 / 方法 / 脚本内部的阅读体验，重点检查“入口注释之外”的复杂处、易混处和关键处。

对清单中的每个代码文件，检查是否存在以下需要内部注释的位置：

- **多步骤流程**：一个函数内连续完成 3 个以上步骤，例如读取配置 → 查询数据库 → 转换结果 → 组装响应。
- **复杂分支**：`if/elif/else`、异常兜底、早返回、权限分流、安全拦截等会影响行为走向的地方。
- **新手不直观的技术点**：例如 SQLAlchemy 查询、Alembic metadata、sqlglot AST、Pydantic Schema、FastAPI 依赖注入、TestClient 依赖覆盖等。
- **数据结构转换**：例如 ORM 对象 → Pydantic、RowMapping → dict、Decimal/datetime → JSON、YAML → 内部对象等。
- **安全 / 权限 / 校验逻辑**：例如 SQL Guard、敏感字段、RBAC、参数校验、危险操作拦截。
- **关键业务口径**：例如 GMV、退款率、时间窗口、固定业务事实、评测标准答案等。
- **容易踩坑处**：例如 循环导入、测试库和主库差异、MySQL / SQLite 方言差异、连接生命周期、trace_id 透传。
- **兜底检查**：连续 20-30 行核心逻辑：不含纯 import / 常量定义 / 装饰器堆叠。如果完全没有注释，必须补步骤注释或关键行注释。

判断标准：

- 如果读者只看函数开头注释，仍然看不懂中间某段为什么这样写，就需要补内部注释。
- 内部注释优先解释“为什么”和“这里在防什么坑”。
- 长函数优先使用步骤注释，并加上分隔线，例如：`# 步骤 1：XXXXX ==========` 和 `# 步骤 1-3：XXXXX ----------`
- 短但关键的逻辑用 `# ★ ...` 点明原因即可。
- 一个文件里的主角函数也需要在docstring添加 ★ 标注。
- 如果某段代码已经通过命名、结构和上下文足够清楚，不要为了凑数量硬加注释。

产出：

- 列出检查到的内部复杂点，以及是否补了注释。
- 示例：`app/api/query.py：为 SQL Guard 拦截分支、RowMapping 序列化、未命中模板路径补充内部注释。`

### 第 4 遍：形式扫描 —— 格式好不好看

这一遍只看形式，不看内容深度：

- **对齐线**：检查 `# 步骤 1：XXXXX` 或 `# 步骤 1-3：XXXXX` 是否有分割线，以及分割线长度是否达标，`==========` / `----------` 分隔线补齐到每行总宽约 100 列（中文按 2 列计），同文件内大致视觉对齐，目测即可。
- ★ 标记密度：关键点是否有 ★，普通流程说明不要滥用；如果同一文件里 ★ 太多导致重点失焦，需要精简。
- **语言**：注释是否以中文为主。大面积英文且无中文解释的，补中文。
- 产出：列出改了哪些文件的格式，如 `app/api/query.py：补 2 处分隔线对齐 + 1 处 ★`。

### 收尾

4 遍扫描完成后，整理阶段 1 小结：

- 补写了几个缺失注释（第 1 遍）
- 深化了几个新概念/设计决策的解释（第 2 遍）
- 修了几处内部注释（第 3 遍）
- 修了几处格式（第 4 遍）

如果本阶段补写/深化了较多注释，或涉及关键设计决策，先把简短素材记入 `.agent_work/temp/<module>-notes.md` 或留给后续 AI_CONTEXT 技术档案使用，避免阶段 3 凭记忆总结。

## 阶段 2：运行验证

1. 先读当前阶段计划文件中本模块的「验证」或「验收标准」小节，确认是否有模块特定的验证步骤（如 eval 脚本、smoke 测试）。有则优先执行；没有则只跑通用命令。
   
2. 通用验证命令（以 CLAUDE.md 指定的项目 Python 路径为准）：

   Windows / PowerShell 常用：

   ```powershell
   $env:PYTHONDONTWRITEBYTECODE='1'
   # 测试（所有模块）
   <项目 Python> -m pytest -p no:cacheprovider

   # 数据库迁移检查（涉及 ORM / Alembic 时）
   <项目 Python> -m alembic check
   <项目 Python> -m alembic current

   # seed 数据完整性（涉及 seed 时）
   <项目 Python> -m scripts.seed_data --reset
   ```

   macOS / Linux 可用：

   ```bash
   PYTHONDONTWRITEBYTECODE=1 "<项目 Python>" -m pytest -p no:cacheprovider
   PYTHONDONTWRITEBYTECODE=1 "<项目 Python>" -m alembic check
   PYTHONDONTWRITEBYTECODE=1 "<项目 Python>" -m alembic current
   PYTHONDONTWRITEBYTECODE=1 "<项目 Python>" -m scripts.seed_data --reset
   ```

3. 记录要求：

- 记录命令是否成功
- 记录关键输出结论
- 有 warning 要说明是否影响本模块
- 命令失败时，不要掩盖；写明失败原因和是否阻塞

## 阶段 3：更新 AI_CONTEXT.md / AI_CONTEXT_CHANGELOG.md

模块完成时，在 `docs/AI_CONTEXT_CHANGELOG.md`「变更记录」头部新增一节（`###` 标题），保存完整模块档案和实验记录。

同时只把会影响续接判断的最新事实摘要同步到 `docs/AI_CONTEXT.md`，例如当前模块、默认配置、最新评测基线、重要实验结论或活跃坑。`AI_CONTEXT.md` 必须保持短小，不再承载完整历史变更记录。

「变更记录」模板：

```md
### Mx 模块名（YYYY-MM-DD）

- 改动范围：先跑 `git diff --name-only <base>..HEAD`（base 为本模块起始 commit）获取完整变更清单，再归并为 glob 模式（如 `engine/nl2sql/*`、`app/schemas/agent.py`），归并后逐条对照原始清单确认无遗漏。如果无明确起始 commit，用 `git status --short` 和 `git diff --stat --cached` 代替。
- 关键记录：
  - 比如关键决策、决策原因、实验结果、新发现、用户做出的选择
- 参考资料：
  - 查了什么，借鉴了什么，没照搬什么；如果未查阅，写“无”
- 验证快照：
  - pytest：结果
  - alembic / seed / API / eval：结果
  - warning：是否影响
- 遗留/后续：
  - 比如：下一模块要接什么，当前还有什么风险，后续采用什么技术或方法
```

同时更新 `docs/AI_CONTEXT.md` 顶部「当前状态」：「上一模块验收」在收工时填「Mx 未验收（待 accept-module）」（Mx = 本次收工的模块）；验收通过后由 accept-module 改写，本 skill 不代填「已验收」。

如果只是小修复，不写完整档案，只在 `AI_CONTEXT_CHANGELOG.md`「变更记录」新增一个 `###` 条目（内容 1-3 行）；仅当它影响当前路线时，再同步一句到 `AI_CONTEXT.md`「最新事实快照」：

## 阶段 4：更新 dev-log.md（最重要的阶段）

只有模块完成时在 `docs/dev-log.md` 末尾追加新的模块记录，小修复则不更新。本文档给用户读，新手友好，不给 AI 堆上下文。不写没实现的能力，没记录到的过程细节就写“过程细节未记录”。

模块记录的各个小节都要用 `**...**` 加粗标出关键词、核心决策、类比锚点、量化成果和面试 talking point 等。加粗服务于一眼抓重点，新手扫读友好，不要整句加粗。

按照以下模板的要求写：

````md
## ★ Mx 模块名

（YYYY-MM-DD）

**简述**：一句话说明模块定位和结果

### 先用大白话讲

先说这个模块解决什么问题，不讲代码细节。
适当用生活类比或工程类比。
虽然用大白话，但是还是要把这个模块的关键设计覆盖全。
最后用一句话收束：所以本模块的核心价值是……

### 这次做了什么

用故事体写：为什么要做 → 怎么做 → 得到了什么结果。要求通俗易懂、完整详细、条理清晰。

### 新概念

用编号列表写，每一项格式为：

1. **职责标题**：`文件或目录`
   说明这个文件负责什么；点名主角类 / 函数 / 常量；说明阅读重点，需要理解什么，不需要死抠什么。本部分的写作细则见下方“「代码阅读路线」写作细则”。

列表后可补充核心调用链或数据流向，例如：

`HTTP 请求`
→ `Schema`
→ `Engine / Service`
→ `DB`
→ `Response`

**模块闭环**：（可选）当本模块与之前模块共同构成可演示的完整能力时写这一节，否则跳过。根据项目实际情况写，可长可短。

### 设计要点

- 关键决策 1：为什么这样选
- 关键决策 2：为什么没用临时方案
- 风险或边界：哪里后续要继续补

2. **[工程/深挖追问] 真实问题？**

   这里写回答正文。

3. **[压力追问] 真实问题？**

### 验证与下一步

- 验证：写真实跑过的命令结论
- 下一步：下一模块入口

可复制验证命令：

```powershell

```

**本地启动体验：**

（模块具备可交互后端能力时必须写。优先写成用户能直接照做的体验流程，参考 SpringBoot 项目的 Swagger / Knife4j：准备数据库/seed → 启动 API 服务 → 打开 Swagger UI / 浏览器接口文档 → 填 JSON 或参数 → Execute → 说明大致返回结果。
````

### 「代码阅读路线」写作细则

「代码阅读路线」必须回答：从哪里开始读、每一步看什么、这些文件如何协作。每个编号项默认包含以下信息；短小文件、纯报告文件等可合并说明，避免为凑规则写成长段。

- 从哪个入口开始读；如果这一步是流程代码，说明它接收什么、产出什么；如果是配置 / 报告 / 文档，说明它被谁消费、解决什么问题。
- 点名这一段的关键设计，并用 1-2 句解释它解决了什么问题、为什么这样放在这里；不要只写“重点理解 XXX”。
- 如果有容易分散注意力的细节，说明哪些实现细节可以先跳过。

根据文件长度或作用控制单项长度。优先使用 **加粗关键词** 标出阅读锚点。面向新手学习和理解，避免写成冗长的函数说明；如果一个文件承担多步流程，用“先看...然后看...最后看...”组织。以下是2个较长的文件的示例：

```
2. **评测执行**：`eval/run_eval.py`
   可以按“一条 case 的旅程”来读：先看 `main()`，它负责串起参数、用例、执行和报告。然后看 `load_cases()` 如何把 YAML 变成 `EvalCase`；`seeded_api_client()` 如何用 **内存 SQLite + dependency override** 复用真实 API；`run_cases()` 如何调用 `/api/query`；最后 `write_report()` 如何生成 Markdown 报告。重点理解这里验证的是 **API seam**，不是内部函数；这样能同时检查 API 契约、Trace、图表字段和安全拦截，不会因为绕过路由而漏掉真实调用链问题。
   
3. **Seed 数据工厂**：`scripts/seed_data.py`
主角是 `seed_database()` 和 `verify_business_facts()`。前者按父表、事实表、桥接表、宽表的顺序生成数据；后者用真实 SQL 查固定事实。读的时候重点看：外键靠 ORM 对象关系，不靠自增 ID；固定事实靠 `sku/coupon_code/channel_code` 等业务键，不靠 `id=1`。
```

### 「面试怎么讲」写作细则

```
追问难度分层：

- [基础追问]：用于训练用户把模块讲清楚。问题可以问模块目标、核心概念、主流程，但不能只是纯概念定义，也不能是送分题。回答要体现用户真的理解这个模块，而不是背名词。
- [工程/深挖追问]：用于训练真实工程判断，问题必须带一点压力。问题可以追问设计取舍、失败场景、降级策略、数据边界、安全边界、评测口径、可维护性、扩展性、技术债、后续路线等。回答要能落到本模块的代码、验证、风险和取舍上。
- [压力追问]：用于模拟资深面试官的一针见血式质疑。问题可以带有不完全友好的预设，也可以没有标准答案，重点训练用户如何承认边界、澄清目标、给出证据、说明取舍，并把问题拉回本模块真实工程价值。不要为了展示模块优点而设计问题；这类问题应该让回答者感觉“有点难接”。

数量要求：

- 追问数量根据模块范围、复杂度和面试价值灵活调整。
- 小模块可以只写 1 个基础追问 + 1 个工程/深挖追问，不为了凑数量强行写问题；关键模块可以增加 `工程/深挖追问` 或 `压力追问`，覆盖关键点和可能的弱点。
- 涉及架构、数据库、安全策略、评测体系、可观测性、长期路线，或者存在明显争议点 / 不完美结论 / “是不是过度设计”质疑空间的模块，优先增加 `压力追问`。

问题优先覆盖：

- **设计取舍**：为什么这个复杂度值得加？有没有更简单方案？为什么没选？
- **失败场景**：如果这个模块误判、超时、不可用、召回漏掉、写入失败，会怎样？
- **验证证据**：你怎么证明它有效？看了哪些测试、指标、trace、eval 或 smoke？
- **扩展边界**：数据量、业务复杂度、Agent 步骤变多后怎么演进？
- **技术债**：当前哪些地方是刻意没做的？为什么现在不做？
- **口径一致性**：本地报告、trace、LangFuse、eval 之间如何避免各说各话？

禁止写低价值问题：

- 不写“X 是不是必须的？”这种答案显然是否定的问题。
- 不写“为什么不用 X？”但回答只是复述当前方案优点的问题。
- 不写纯概念定义题，例如“什么是 TraceRouter？”
- 不写问题里已经暗示答案的提问，例如“为什么你选择了更稳定的方案？”
- 不为了凑数量强行写问题。
- 不把模块优点包装成面试官提问。
- 压力追问可以尖锐，但不能胡搅蛮缠；问题应基于本模块第一段叙述、真实边界或明显争议点提出，而不是凭空否定项目。

对于[压力追问]，回答时不要硬装完美。推荐顺序：

1. 先承认对方质疑里合理的部分。
2. 再澄清本模块的真实目标和边界。
3. 然后给出已经验证过的证据。
4. 最后说明如果进入下一阶段，会怎么补齐。

压力追问举例（`→` 表示回答完前一个问题后紧接着的追问）：

- “你这个 Agent 到底解决了什么现有方案没解决的问题？”
- “你怎么保证上下文不超限？超了怎么办？” → “上限多少？你实测过没？”
- “你说压缩了 82% token，怎么算的？基线是什么？” → “你说你只在小PR上跑过，那如果 PR 改 20 个文件呢？”
- “你的 code review 项目遇到低风险改动直接跳过大模型，怎么判断？” → “ A=1 改成 A = 1 语法树变不变？” → “那 A=1 改成 A=2 呢？”
- “你科研项目里的多 Agent 协作，信息传递怎么保证不丢失？” → “那内容语义呢？上一个 Agent 的推理过程怎么传给下一个？”
- “AI云硬件对延迟和稳定性要求高很多，你在这方面有没有经验？”
- “有没有量化指标、日志埋点？”
- “那如果场景变了呢？” → “还有呢？” → “有什么问题？”
- “你这部分做了挺多工作但业务能力没有明显提升，这是不是偏工程自嗨？”
```
