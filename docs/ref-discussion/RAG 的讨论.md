**4. **

```
最近review几个RAG项目,发现一个普遍现象：所有人都说自己做的是"Agentic RAG",但代码一拉:retrieve一次 → stuff到context → 让LLM生成。这哪门子agentic?说5个踩坑总结的关键能力:

1. 检索决策本身就是个能力。
不是每个query都要检索——闲聊、常识、上下文已有答案的都不该搜。强行每次检索浪费token还引入噪声干扰生成。实测:加上"要不要检索"判断后,延迟降30%,准确率反升8个点。检索是工具,不是默认动作。

2. Query Rewriting决定召回上限。
用户的query是给人看的,不是给检索系统看的。要做改写、多hop拆解、HyDE、step-back。90%的召回不准是query问题,不是embedding问题。

3. Context Engineering > Retrieval Quality。
检索回top-50全塞进去,效果可能比top-5还差(Lost in the middle)。真正决定质量的是检索之后:rerank、去重、排序、压缩、预算控制。护城河在retrieval之后,不是之前。

4. Self-Reflection Loop才是Agentic的灵魂。
分水岭不是用了LangGraph,而是模型能不能判断"检索回来的够不够用",不够就refine query再搜。没这个loop,你做的就是naive RAG包层壳。

5. 别用Ragas套现成指标评Agentic RAG。
要测检索时机准确率、loop终止合理性、reflection准确率、上下文利用率。用naive RAG指标评Agentic RAG,看到的"好"是假的。
```

**7.**

```
Agentic RAG 和普通 RAG 的区别，从文档进入系统那一刻就已经分道扬镳了，根本不是检索完之后才加个智能体这么简单。
	
先说普通 RAG。它的流程就是一条单向流水线，原始文档进来，固定规则切块，向量化，存进向量库，用户提问的时候检索一次 Top-K，拼成 Context 丢给 LLM 生成答案。整个过程只走一遍，没有回头路。切块方式是死的，不管什么文档都用固定长度切。检索只做一次，结果好不好都不会回头再查。没有反思机制，LLM 拿到什么就用什么。表格标题这些结构信息在切块那一刻就被拍扁成纯文本了。
	
Agentic RAG 不一样。它的文档处理阶段就已经开始做语义分块和层级化索引，表格图表标题这些结构化信息会单独建模保留。检索阶段支持多轮迭代，Agent 会做查询改写和分解，第一轮结果不够就生成新的检索请求继续查。最关键是它有自我评估环节，生成答案之前会先问自己这些资料够不够回答问题，要不要换个关键词再试一次。而且它还能做任务规划，把一个复杂问题拆成多个步骤，检索只是其中一部分，后面的提取、比对、生成变更说明都是普通 RAG 完全不具备的能力。
	
一句话来说，Agentic RAG 不是 RAG 加个 Agent 的壳，而是用 Agent 的规划、反思和工具调用能力，把一次性检索升级成了可以自主决策、自主纠错的任务执行过程。
```

**8.**

```
传统 RAG 像图书管理员：用户提问后，只做一次检索、一次生成，速度快、成本低，适合简单直接的问题。但当问题变成多跳推理、模糊查询、多数据源检索或需要判断检索质量时，标准 RAG 就容易失效。
Agentic RAG 则像研究员：由 AI Agent 主动控制检索流程，先判断是否需要检索，再选择工具、改写查询、评估结果，并在信息不足时继续检索，直到能够更可靠地回答。它的核心不是“多检索几次”，而是让 Agent 在每一步做决策。
Agentic RAG 通常由三部分组成：Agent 负责思考与判断，Tools 提供向量库、SQL、网页、知识图谱等外部能力，Loop/Memory 负责把每一步结果记录下来并持续迭代。常见模式包括 ReAct-style RAG、Self-RAG 和 Corrective RAG，分别强调推理行动循环、检索质量自检和失败后的兜底检索。
所以，简单问题选 Standard RAG，更快更省；复杂问题、多源问题、研究/法律/医疗等高准确性场景，更适合 Agentic RAG。它更强，但也意味着更高延迟、更高成本和更复杂的系统设计。
```

**9.**

```
Multi-Agent RAG：一群Agent协同作战，核心是加了个“总指挥”——Aggregator Agent
- Memory分短期和长期，Planning用ReAct、CoT这类
- Aggregator Agent 把任务拆分，派给下面的Agent 1/2/3分头去干活
- 每个小 Agent 各管一摊：
- Agent 1 → 本地数据服务器（本地文件、图片、视频）
- Agent 2 → 搜索引擎（比如Kagi）
- Agent 3 → 云引擎（AWS、Azure）
- 都是通过 MCP Servers 统一对接各种数据源
- 最后所有结果汇总回 Aggregator Agent，再交给生成模型输出
特点：分工协作 + 统一调度，能处理更复杂、跨数据源
```
