# Module Finish · Docs（dev-log 学习复盘写作）

开始写作前，必须在 `<module>-notes.md` 中找到最近一次 `finish-module 技术档案交付清单`，并确认全部为 `[x]`。清单不存在、存在未完成项，或明确写着 `finish-module 未完成` 时，停止并提醒用户先 `finish-module`。

使用本 skill 必须阅读「强制执行门（硬门禁）」。本 skill 的唯一内容交付物是 `docs/dev-log.md`；允许在 `docs/notes/<module>-notes.md` 中追加执行清单和检查结果。

## 强制执行门（硬门禁）

- 必须完整读取本 `SKILL.md` 至 EOF。
- 完整读取当前 `<module>-notes.md` 至 EOF。
- notes 缺少范围、关键决策、验证、风险、遗留或 Handoff 时，停止并退回 `finish-module`。
- 本阶段不运行模块验证；除 `docs/dev-log.md` 和 `<module>-notes.md` 外，不修改代码或其它文档。发现其它位置的问题时，只在会话中提醒用户。
- dev-log 交付门、完整回读和 `git diff --check` 未完成时，不得声明 `finish-docs` 完成。

## 核心原则

过程细节未记录就不编。复盘编写的信息来源按以下优先级使用：

- `docs/notes/<module>-notes.md`（模块收工素材的单一事实源）
- 会话记忆（开发和收工是同一个 AI 会话时可用）
- `docs/state/AI_CONTEXT.md`
- `docs/state/CHANGELOG_INDEX.md` 及其路由到的本模块 Phase 文件
- git diff

素材缺失分为两类：

- **完成关键素材缺失**：包括模块验证快照、关键决策及最终选择、实际改动范围、风险、安全或兼容边界、遗留事项。缺少任一项时必须停止 `finish-docs`，列出缺项并退回 `finish-module` 补齐。
- **非关键过程细节缺失**：例如某次中间排查的完整过程。允许如实写“过程细节未记录”，但不得据此推测、补写或美化结论。

`finish-docs` 不得新跑数据库、API、smoke、pytest、Eval 或真实 LLM 等模块验证来补造素材，也不得补写或修订 AI_CONTEXT / CHANGELOG；本阶段只能运行文档回读、Git 范围核对和 `git diff --check` 等交付检查。若技术档案未完成或与 notes 明显冲突，停止并退回 `finish-module`。

## 阶段 1：读取和检查素材

严格按以下顺序执行：

1. 完整读取 `docs/notes/<module>-notes.md`。
2. 找到最近一次 `finish-module 技术档案交付清单`，全部为 `[x]` 时继续。
3. 检查 notes 是否包含：模块范围；关键决策及最终选择；真实验证快照；风险、安全与兼容边界；遗留事项；Handoff。
4. 完成关键素材缺失时，列出缺项并停止。
5. 读取 `docs/state/AI_CONTEXT.md` 的当前模块和最新事实。
6. 完整读取 `docs/state/CHANGELOG_INDEX.md`，再按索引读取本模块技术档案，只读核对 notes 与正式结论一致。
7. 运行 `git status --short`、`git diff --name-only` 和 `git diff --name-only --cached`，核对 notes 记录的模块范围。
8. 只有上述检查全部通过后，才在 notes 中新增“finish-docs 执行清单”，初始均为 `[ ]`。

完成关键素材缺失时必须退回 `finish-module`。只有非关键过程细节缺失时，才允许写“过程细节未记录”后继续。

### 「这次做了什么」写作细则

这一节不是改动清单，而是对一次工程工作的完整解释。读者读完后应能理解：系统原来为什么会出问题，这次到底改变了什么，为什么这样改，以及如何证明没有把问题改坏。

先写一段概览，说明本模块处理的核心矛盾、最终结论和对项目的实际价值。

随后分编号围绕本模块最重要的工作展开。每个关键点都要写清楚：

- 原来的问题是什么：描述真实行为、误判、风险、用户影响或评测影响。不要只说“存在 bug”，要说明 bug 会导致什么错误判断或错误结果。
- 核心概念怎么理解：如果涉及术语，先用不依赖代码背景的语言解释它在系统里的角色，可使用类比。术语首次出现时，保留英文/代码名，但紧跟一句普通语言解释。
- 这次如何解决：说明关键机制、规则、数据流或架构边界。点名承担职责的代码位置，但重点是解释“它负责解决什么”，不是罗列“改了哪个文件”。
- 为什么不采用更宽松或更简单的方案：如果存在安全、数据正确性、兼容性、评测可信度或长期维护风险，要说明保守边界和取舍。
- 结果怎样证明：写真实测试、trace、smoke、eval、反例或人工审计结论，并解释这些证据分别证明了什么，以及下一步大致是什么方向。
- 还不能说明什么：明确区分“已经证实的确定性修复”和“尚未建立的端到端能力结论”，避免把测试通过写成能力全面提升。

应自然使用 **加粗** 突出：**核心问题**、**关键机制**、**安全或业务边界**、**验证证据**、**尚未完成的结论**。不要整段加粗，不要把代码改动逐行翻译成文字。

语言通俗易懂，让不了解实现细节的读者也能理解；完整详细，适合复盘。

### 「面试怎么讲」写作细则

追问难度分层：

- [基础追问]：用于训练用户把模块讲清楚。问题可以问模块目标、核心概念、主流程，但不能只是纯概念定义，也不能是送分题。回答要体现用户真的理解这个模块，而不是背名词。
- [工程/深挖追问]：用于训练真实工程判断，问题必须带一点压力。问题可以追问设计取舍、失败场景、降级策略、数据边界、安全边界、评测口径、可维护性、扩展性、技术债、后续路线等。回答要能落到本模块的代码、验证、风险和取舍上。
- [压力追问]：用于模拟资深面试官的一针见血式质疑。问题可以带有不完全友好的预设，也可以没有标准答案，重点训练用户如何承认边界、澄清目标、给出证据、说明取舍，并把问题拉回本模块真实工程价值。不要为了展示模块优点而设计问题；这类问题应该让回答者感觉“有点难接”。压力追问的回答的最后一个句号 `。` 换成 `喵。`。

数量要求：追问数量根据模块范围、复杂度和面试价值灵活调整。小模块可以只写 1 个基础追问 + 1 个工程/深挖追问，不为了凑数量强行写问题；关键模块可以增加 `工程/深挖追问` 或 `压力追问`，覆盖关键点和可能的弱点。

禁止写低价值问题：

- 不写“X 是不是必须的？”这种答案显然是否定的问题。
- 不写“为什么不用 X？”但回答只是复述当前方案优点的问题。
- 不要追问已明确安排在后续模块优化的能力，尤其避免用后续目标质疑当前阶段，再以“后续会升级”作答。这类问答只是复述既定路线，没有实际价值。
- 不写纯概念定义题，例如“什么是 TraceRouter？”
- 不写问题里已经暗示答案的提问，例如“为什么你选择了更稳定的方案？”
- 不为了凑数量强行写问题。
- 不把模块优点包装成面试官提问。
- 压力追问可以尖锐，但不能胡搅蛮缠；问题应基于本模块叙述、真实边界或明显争议点提出。

问题优先覆盖：

- **设计取舍**：为什么这个复杂度值得加？有没有更简单方案？为什么没选？
- **失败场景**：如果这个模块误判、超时、不可用、召回漏掉、写入失败，会怎样？
- **验证证据**：你怎么证明它有效？看了哪些测试、指标、trace、eval 或 smoke？
- **扩展边界**：数据量、业务复杂度、Agent 步骤变多后怎么演进？
- **技术债**：当前哪些地方是刻意没做的？为什么现在不做？
- **口径一致性**：本地报告、trace、LangFuse、eval 之间如何避免各说各话？

对于[压力追问]，回答时不要硬装完美。推荐顺序：

1. 先承认对方质疑里合理的部分。
2. 再澄清本模块的真实目标和边界。
3. 然后给出已经验证过的证据。
4. 最后说明如果进入下一阶段，会怎么补齐。

压力追问举例：

- “你这个 Agent 或者方法到底解决了什么现有方案没解决的问题？”
- “你怎么保证上下文不超限？超了怎么办？你实测过上限没？”
- “你说压缩了 82% token，怎么算的？基线是什么？你说你只在小PR上跑过，那如果 PR 改 20 个文件呢？”
- “你的 code review 项目遇到低风险改动直接跳过大模型，怎么判断？”
- “你科研项目里的多 Agent 协作，信息传递怎么保证不丢失？”
- “我们对延迟和稳定性要求很高，你在这方面有没有经验？”
- “你这部分做了挺多工作但业务能力没有明显提升，这是不是工程自嗨？”
- “有没有量化指标、日志埋点？”
- “你这个项目如果场景变了还能适用吗？”
- “这也能叫 Agent 吗？是不是为了用 LangGraph 而用 LangGraph？”
