# Module Finish（模块技术收工）

本 skill 负责模块完成后的整套**技术收工**：**补注释 + 跑验证 + 固化 notes + 通过 CHANGELOG_INDEX 更新当前 Phase 技术历史与 AI_CONTEXT**。它不写面向用户学习复盘的 `dev-log.md`（由 `finish-docs` 负责），也不是最终验收门禁（由 `accept-module` 负责）。

```text
finish-module（本 skill：注释 + 验证 + notes + 技术档案）
        ↓
finish-docs（只写 dev-log 学习复盘）
        ↓
用户人工看一遍，可要求小修
        ↓
accept-module（最终门禁检查）
```

三个 skill 独立调用，不互相嵌套。**必须在开发刚结束时调用**——本 skill 依赖对话里的新鲜上下文（决策、踩坑、验证输出），并趁这些事实仍然清晰时完成技术档案；一旦上下文丢失，素材就只能靠 notes.md 和 git diff 还原。

## 核心原则

过程细节未记录就不编。

如果从以下来源都找不到某个决策、踩坑或命令信息：

- 当前对话
- `docs/state/AI_CONTEXT.md`
- `docs/state/CHANGELOG_INDEX.md` 及其路由到的相关 Phase 文件
- `docs/notes/<module>-notes.md`
- git diff
- 终端验证输出

那就在 notes 或技术档案中写“过程细节未记录”，不要脑补合理故事。

验证快照必须来自本 skill 实际跑过的命令，或来自当前对话中明确可见的真实命令输出。不能写“预计通过”“应该通过”。

## 阶段 0：确认范围和素材

1. 完整读取：
   - `AGENTS.md` 或 `CLAUDE.md`
   - `docs/notes/<module>-plan.md`
   - `docs/notes/<module>-notes.md`
   - `docs/state/AI_CONTEXT.md`

2. 确认模块名称、范围、验收标准和明确不做的内容。

3. 收集最终文件范围：
   - 始终运行 `git status --short`、`git diff --name-only` 和 `git diff --name-only --cached`。
   - 有模块起始 commit 时，再运行 `git diff --name-only <base>`。
   - 模块部分已提交时，结合 `git log --oneline <base>..HEAD`。
   - 归并已提交、未暂存、已暂存和未跟踪文件；排除不属于本模块的用户改动。
   - 起始 commit 不明确时，在 notes 和 changelog 中如实说明依据。

4. 收集当前对话、notes、验证输出和关键决策素材。需要追溯历史时，先读 `CHANGELOG_INDEX.md`，再进入其路由文件。

5. 根据当前文件清单和 notes 新事实生成初步 `state impact map`，供验证阶段读取运行条件。阶段 4 再依据最终改动重新核对。

6. 审计 Live Dev Probe 时点证据：对照 plan 的 Probe ID/checkpoint，确认 notes 已记录计划/实际时点、被阻塞切片、执行时间、当时代码阶段、HEAD 与模块相关 dirty 文件、命令与真实依赖、本次/模块累计 calls/tokens 及授权来源/剩余、Response/Trace identity、总体与关键子能力三态、失败层/根因假设/最小判别动作、`continue/revise/stop` 决定和 exploratory/baseline-ineligible 边界，并能从 Probe → 决策 → 后续修改/重验的顺序看出它确实影响了开发。HEAD 只代表提交基线，不能单独证明未提交工作树；最终代码下的一次性结果也不能反推成开发期证据。

7. 适用模块若缺少上述证据，立即在 notes 标记 `development_probe_missing`，声明本次 `finish-module 未完成` 并返回开发流程；不得继续到阶段 1–4，也不得在本 skill 内首次补跑后直接消除缺口。完成缺失 Probe、必要定位/修复和最小重验后，重新调用本 skill。按计划时点真实尝试但依赖不可用的 `inconclusive` 不算缺失，但必须有 contemporaneous（当时写入的）记录。

## 阶段 1：注释审查

目标：把本模块代码的注释从"开发时顺手写的"提升到"复盘时能读懂的"。

完整阅读阶段 0 归并出的所有本模块代码文件，不抽样；不处理无关用户改动。

### 1. 覆盖

检查模块级职责、类、非豁免函数/方法是否有足够的 docstring 或开头注释。豁免仅限空 `__init__.py`、纯 re-export、简单字段模型、简单赋值初始化和明显自解释的局部闭包。

缺失项必须补写。notes 只记录总数、补写数和仍缺失数，不要求保存逐符号表格。

### 2. 质量

这一遍只关注注释的**内容深度**，不关注格式。从本模块代码中挑出：

- **每个新概念**（本模块第一次出现的术语、技术、模式）：用通俗语言解释了吗？一个没学过这个概念的读者能看懂吗？必要时有没有类比？如果没有，补写到"能懂"为止。
- **1-3 个关键设计决策**（模块最重要的架构选择）：相关注释是否解释了“为什么这样做”？如果有明显替代方案，是否解释了“为什么不用另一个方案”？如果只写了“做什么”没写“为什么”，补写理由。

### 3. 可读性

这一遍只看函数 / 方法 / 脚本内部的阅读体验，重点检查“入口注释之外”的复杂处、易混处和关键处。

对清单中的每个代码文件，检查是否存在以下需要内部注释的位置：多步骤流程 / 复杂分支 / 新手不直观的技术点 / 数据结构转换 / 安全逻辑 / 关键业务口径 / 容易踩坑处。

- 如果读者只看函数开头注释，仍然看不懂中间某段为什么这样写，就需要补内部注释。
- 内部注释优先解释“为什么”和“这里在防什么坑”。
- 长函数优先使用步骤注释，并加上分隔线，例如：`# 步骤 1：XXXXX ==========` 和 `# 步骤 1-3：XXXXX ----------`
- 重要逻辑用 `# ★ ...` 点明原因；一个文件里的主角函数也需要在docstring添加 ★ 标注。只标真正关键点。
- 如果是在已有文件的代码上进行了修改，那么之前原有的注释可能会过时，需要更新。
- 如果某段代码已经通过命名、结构和上下文足够清楚，不要为了凑数量硬加注释。

### 4. 形式

- **对齐线**：检查 `# 步骤 1：XXXXX` 或 `# 步骤 1-3：XXXXX` 是否有分割线，以及分割线长度是否达标，`==========` / `----------` 分隔线补齐到每行总宽约 100 列（中文按 2 列计），同文件内大致视觉对齐，目测即可。
- ★ 标记密度：关键点是否有 ★，普通流程说明不要滥用；如果同一文件里 ★ 太多导致重点失焦，需要精简。
- **语言**：注释是否以中文为主。大面积英文且无中文解释的，补中文。

### 收尾

在 notes 中简要记录：

- 检查了多少本模块代码文件和非豁免类/函数；
- 实际补写了多少缺失注释；
- 深化了哪些新概念或关键设计决策；
- 修正了哪些复杂处或过时注释；
- 是否仍有缺失。

## 阶段 2：运行验证

1. 先读取：
   - 当前 module plan 的验证与验收要求；
   - `docs/state/runbook.md`；
   - 读取初步 `state impact map` 中与本轮验证条件有关的专项 state。
2. 按以下顺序验证：
   - 先运行与本模块改动直接相关的聚焦测试、合同测试、smoke 或静态检查。
   - 失败时先定位和修复相关用例，不立即重复运行全仓测试。
   - 代码和验证条件未变化，且当前对话已有可信结果时，不重复运行同一验证。
   - Live Dev Probe 的常规执行必须已发生在开发切片中；本阶段只复核其结果是否仍对应当前代码与运行条件，不把收工验证当作首次真实路试。开发期 Probe 后相关代码或真实条件发生实质变化时，退出本 skill，回到开发流程执行 plan 允许的最小重验，再重新收工。
   - 完成代码修改后，再按 plan 和 AGENTS 要求运行完整回归。
3. Live Dev Probe 审计：
   - 按阶段 0 第 6 条的字段清单逐 Probe 核对；另确认首个 Probe 发生在第一条真实纵向链路可运行后、依赖结果的后续切片前，并检查禁区边界。HTTP 200、最终代码下的补跑或只有 fake 证据都不能满足此门。
   - 若 Probe 当时触发 `revise`，必须看到对应问题定位、代码/配置修正、聚焦测试和额度内最小重验的时间顺序；失败 attempt 必须保留。
   - 若 plan 判断不适用，检查理由是否与代码真实影响面一致；若按时尝试但环境不可用，确认 `inconclusive`、preflight 和失败层已在当时记录。
   - 任一项缺失都按阶段 0 的 `development_probe_missing` 处理，不能继续技术收工。模块回复仍需提醒用户下一步是否值得执行哪一种 Formal Eval。
4. 长时间命令：
   - 预计超过 2 分钟的完整 pytest、Eval、构建或数据处理任务，遵守 AGENTS 的后台任务规则。
   - 启动后台任务前先完成 notes 阶段性 checkpoint；启动后记录任务指针并标记“运行中，待检查”，然后再按 AGENTS.md 的要求向用户报告并结束当前回复。
   - 日志、退出码和完成标记写入 `.agent_work/temp/`。
   - 后台任务未完成或结果尚未检查时，不得宣称模块完成。
   - Formal Eval 继续遵守 runbook 的单次授权、唯一 `run_id` 和禁止自动重跑规则；不要把 Live Dev Probe 的 standing authorization 扩大成正式 Eval 授权。
5. 条件验证：
   - 涉及 ORM / Alembic 时运行 `alembic check` 和 `alembic current`。
   - `scripts.seed_data --reset` 会重建目标数据库，只有 module plan 明确要求，或用户已经授权本轮重置时才能运行；执行前确认目标数据库。
   - 涉及文档链接或路径时，检查新增/修改链接的目标是否存在。
6. 每条验证都记录：
   - 命令和退出状态；
   - 关键结果与数量；
   - warning 是否影响本模块；
   - 失败原因、是否阻塞以及是否重跑。


## 阶段 3：素材固化

把本模块收工所需的全部素材写入 `docs/notes/<module>-notes.md`（文件已存在则更新追加）。**这一步是硬要求**：阶段 4 写技术档案、`finish-docs` 写 dev-log 时都以 notes.md 为核心事实源；素材不落盘，后续只能写“过程细节未记录”。

notes.md 必须包含以下小节：

- **模块名称与改动文件清单**：模块名、`git diff --name-only` 归并后的文件范围
- **关键决策与取舍**：决策内容、决策原因、当时给出的选项、主要风险、推荐方案、用户最终选择（如果曾向用户确认过）
- **阶段 1 注释小结**：检查范围、补写的缺失注释、深化的新概念或设计决策、修正的复杂处或过时注释，以及是否仍有缺失
- **阶段 2 验证快照**：每条命令的结论（数字、输出要点）、warning 是否影响、失败原因与是否阻塞；不能只写"验证通过"
- **Live Dev Probe 开发时间线**：是否适用及理由；适用时按阶段 0 第 6 条的字段清单逐 Probe 固化，并保留修复与最小重验的时间顺序；仅收工时补跑必须标 `development_probe_missing`，不能省略
- **参考资料**：查了什么，借鉴了什么，没照搬什么；未查阅写"无"
- **Handoff**：负责下一模块交接事实，不负责提前制定下一模块。至少包含：
  1. **已完成且可依赖**：已经实现并通过验证的能力、合同、接口和产物。
  2. **未完成与风险**：未证明内容、当前限制和不能外推的结论。
  3. **必须延续的边界与决策门**：用户已确认的长期选择，以及重新决策的触发条件。
  4. **下一模块入口与必读指针**：建议先解决什么、从哪些文件/章节/测试开始；只给建议，不提前冻结实现。不写“先人工审查 / 先运行 accept-module”。

如果某个素材确实缺失（开发时没有记录），在 notes.md 里明确写"过程细节未记录"，不要脑补。

## 阶段 4：更新技术档案（硬门禁）

阶段 4 负责索引指定的当前 Phase changelog、`docs/state/AI_CONTEXT.md`，以及本模块命中的专项 state。必须在阶段 1–3 完成、验证快照和 Handoff 已写入 notes 后执行；不得先写档案再倒推素材。

### 强制顺序

1. **确认事实入口**
   - 使用阶段 0 已读取的 `AI_CONTEXT.md`；如果 `AI_CONTEXT.md` 在阶段 0 后被其他改动更新，重新完整读取。
   - 完整读取 `CHANGELOG_INDEX.md`，并按索引定点读取当前 Phase 近期条目。
2. **确认最终范围与 State 影响面**
   - 重新运行最终 Git 清单，与 notes 中的模块范围核对。
   - 根据 Git 改动和 notes 新事实生成 `state impact map`。
   - 完整读取所有命中的专项 state；未命中的不读。
3. **建立交付清单**
   - 在 notes 中加入技术档案 checklist 和精简版 `State impact`。
   - 所有 checklist 项初始为 `[ ]`。必须逐项核对并记录真实结果；允许在逐项核对完成后一次性写入勾选状态，但禁止未经核对预先全部标为 `[x]`。
4. **更新档案**
   - 更新当前 Phase changelog、`AI_CONTEXT.md` 和命中的专项 state。
   - 命中但无需修改的，在 notes 中记录理由。
   - 新结论修正历史判断时，在旧条目原位添加 `⚠️ 注`。
5. **回读和一致性检查**
   - 完整回读本次 changelog 新章节、修改后的 `AI_CONTEXT.md` 和所有修改过的专项 state。
   - 核对它们与 notes、代码、测试、Eval 和默认配置不存在冲突、失效描述、重复权威定义或事实夸大。
6. **最终检查**
   - 运行 `git diff --check`。
   - 修改过文档链接或路径时验证目标存在。
   - 把回读、State impact 和检查结果写回 notes。
   - 任一硬门未完成时，声明 `finish-module 未完成`。

### 专项 State 影响面审查

根据 Git 改动和 notes 新事实判断影响面；一个模块可以命中多个专项 state。只完整读取命中文档，不无差别通读 `docs/state/`。

| 影响面                                                      | 常见触发信号                                                 | 检查文档                               |
| ----------------------------------------------------------- | ------------------------------------------------------------ | -------------------------------------- |
| 数据库、seed、ORM、Alembic、SQL 指标/关系                   | 数据库结构、seed、固定事实、指标或权限变化                   | `database-current-state.md`            |
| RAG、Knowledge、语料、release、Evidence、citation、文档 ACL | 知识运行链路、语料身份、回答或安全边界变化                   | `rag-current-state.md`                 |
| Eval 合同、case、scorer、基线、A/B、真实运行                | 分母、Gate、artifact、失败归因或基线变化                     | `eval-baselines.md`                    |
| 运行入口、配置、模型、LangFuse、Trace、命令                 | API、环境变量、启动方式或运行接线变化                        | `runbook.md`                           |
| Schema Retrieval、Milvus、embedding、collection             | 向量后端、embedding、collection 或 schema corpus identity 变化 | `schema-retrieval-milvus-embedding.md` |

命中文档需要检查当前默认、身份、数量、运行接线、能力边界、失效时态，以及与代码、测试、Eval、`AI_CONTEXT.md` 和其他专项 state 的冲突。

- 当前事实变化：替换旧内容，不得只追加新结论。
- 无需修改：在 notes 中记录理由。
- 历史或重复内容：确认已有追溯入口后，从当前 state 退役。
- 涉及核心合同、默认行为、安全边界或后续路线的冲突：暂停并请用户确认。
- 同一详细事实只保留一个权威来源，其他 state 只写摘要和指针。

在 `docs/notes/<module>-notes.md` 记录简短的 `State impact`：

- **已更新**：列出专项 state，并简述触发依据和修改内容。
- **已检查、无需修改**：只列出实际命中但检查后无需修改的文档，并说明理由。
- **未命中**：合并列出其余专项 state；无需逐项解释。全部命中时省略此行。

没有对应项的行可以省略。

### 更新当前 Phase changelog

完整模块在「变更记录」头部新增一节，至少包含：

- **改动范围**：基于 Git 原始清单归并后的模块文件范围，并说明起始 commit 是否明确。
- **关键记录**：重要决策、原因、实验结果、新发现；有用户决策时完整记录选项、影响与风险、建议和最终选择，不能只写“A/B”。
- **参考资料**：查阅内容、借鉴点和明确未照搬的部分；没有则写“无”。
- **验证快照**：真实 pytest / API / seed / eval / smoke 结果、warning、失败及其是否阻塞。
- **遗留/后续**：未完成、未证明、风险和下一模块入口。

小修复只新增 1–3 行简短 `###` 条目。若新结论推翻或修正旧条目，还必须在旧条目原位添加 `⚠️ 注` 指向新结论。

### 更新 AI_CONTEXT

`AI_CONTEXT.md` 只保留会影响后续续接的当前事实，不复制完整历史。按以下顺序处理：

1. **替换**失效的当前状态、默认值、基线或路线判断。
2. **退役**仍有历史价值但已不影响续接的内容；先确认可在 changelog、eval-baselines 或专项 state 追溯。
3. **删除**重复、已完成、已解决或无保留价值的内容。
4. **新增**本模块产生且会影响后续开发、验证、排障或路线选择的事实。

完成后必须确认当前状态、默认值、验证事实、路线判断和活跃坑彼此不冲突。
