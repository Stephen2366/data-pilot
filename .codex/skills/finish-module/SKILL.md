# Module Finish（模块收工整理 · 验证与整理）

本 skill 是模块收工整理的**前半程**，负责三件事：**补注释 + 跑验证 + 把素材固化到 `<module>-notes.md`**。它不写任何文档（AI_CONTEXT / dev-log 由后半程 `finish-docs` 负责），也不是最终验收门禁（由 `accept-module` 负责）。

```text
finish-module（本 skill：注释查漏 + 验证 + 素材固化）
        ↓
finish-docs（技术档案与复盘写作）
        ↓
用户人工看一遍，可要求小修
        ↓
accept-module（最终门禁检查）
```

三个 skill 独立调用，不互相嵌套。**必须在开发刚结束时调用**——本 skill 依赖对话里的新鲜上下文（决策、踩坑、验证输出）；一旦上下文丢失，素材就只能靠 notes.md 和 git diff 还原。

## 核心原则

过程细节未记录就不编。

如果从以下来源都找不到某个决策、踩坑或命令信息：

- 当前对话
- `docs/state/AI_CONTEXT.md`
- `docs/state/AI_CONTEXT_CHANGELOG.md`
- `docs/notes/<module>-notes.md`
- git diff
- 终端验证输出

那就在日志里写“过程细节未记录”，不要脑补合理故事。

验证快照必须来自本 skill 实际跑过的命令，或来自当前对话中明确可见的真实命令输出。不能写“预计通过”“应该通过”。

## 阶段 0：确认范围和素材

1. 读取：
   - `AGENTS.md` 或 `CLAUDE.md`
   - `docs/state/AI_CONTEXT.md`
2. 确认模块范围：
   - 当前模块名称
   - 当前模块验收标准
   - 不属于本模块的内容不要补做
3. 收集改动范围：
   - 优先使用用户提供的模块起始 commit
   - 如果没有 commit，使用 `git status --short` 和 `git diff --stat`
   - 只处理本模块相关文件，不回滚用户改动
4. 收集过程素材：
   - 读取 `docs/state/AI_CONTEXT.md` 当前状态 / 最新事实快照
   - 按需读取 `docs/state/AI_CONTEXT_CHANGELOG.md` 近期变更记录
   - 读取 `docs/notes/<module>-notes.md`，如果存在
   - 查找当前对话中已经跑过的验证命令输出
   - 如果模块中曾向用户确认关键取舍，必须记录当时给出的选项、主要风险、推荐方案和用户最终选择；不要只写最终结论
   - 如果素材缺失，后续日志中明确写“过程细节未记录”

## 阶段 1：注释查漏补缺

目标：把本模块代码的注释从"开发时顺手写的"提升到"复盘时能读懂的"。分 4 遍扫描，每遍独立关注点。

### 前置：确定文件范围

1. 获取本模块变更清单：
   - 如果用户提供了模块起始 commit，跑 `git diff --name-only <base>..HEAD`。
   - 如果用户没有提供模块起始 commit，使用 `git status --short`、`git diff --name-only` 和 `git diff --name-only --cached` 获取当前工作树变更。
   - 如果模块已经部分提交，再结合 `git log --oneline` 和当前模块范围判断。
   - 不确定时不要乱猜，只说明“未提供模块起始 commit，本次按当前工作树变更检查”。

2. 按计数口径剔除豁免项，得到**需检查文件清单**。豁免只适用于无业务逻辑或自解释的结构：空 `__init__.py`、纯 re-export、纯字段模型、只做简单赋值的 `__init__`、明显局部且自解释的内部闭包。若 `__init__` / 闭包包含分支、资源管理、外部依赖、关键状态初始化，则不能豁免。纯字段模型只有在类级 docstring 已解释职责、字段含义已通过命名 / `Field` / 注释足够清楚时，才允许不逐字段补注释。
3. 清单中的文件必须全量检查，不抽样；不属于本模块的用户改动不要顺手重写。

### 第 1 遍：覆盖扫描 —— 有没有

对清单中每个文件，逐个列出模块级 docstring、每个类、每个函数/方法（不含豁免项），标记状态：

| 状态 | 含义                                                         |
| ---- | ------------------------------------------------------------ |
| ✅    | 有 docstring 或开头行内注释                                  |
| ❌    | 完全没有任何解释                                             |
| ⏭️    | 豁免（pytest 函数有自描述名+开头注释、常量子类、纯字段模型等） |

- **所有 ❌ 项必须当场补写注释**，补完后把状态改为 ✅。
- 补写时遵循 CLAUDE.md 或 AGENTS.md 的「代码风格」。
- 产出：一句话结论，如 `23 个类/函数，23 已覆盖（含补写 3 个），0 缺失`。

### 第 2 遍：质量扫描 —— 够不够深

这一遍只关注注释的**内容深度**，不关注格式。从本模块代码中挑出：

- **每个新概念**（本模块第一次出现的术语、技术、模式）：
  - 用通俗语言解释了吗？一个没学过这个概念的读者能看懂吗？必要时有没有类比？
  - 如果没有，补写到"能懂"为止。
- **1-3 个关键设计决策**（模块最重要的架构选择）：
    - 模块很小时，至少说明 1 个最重要的取舍。
    - 模块较大时，优先选影响数据库、架构分层、安全策略、评测结构、响应契约的决策。
    - 相关注释是否解释了“为什么这样做”？
    - 如果有明显替代方案，是否解释了“为什么不用另一个方案”？
    - 如果只写了“做什么”没写“为什么”，补写理由。

- 产出：列出检查了哪些新概念、哪些设计决策，各自补了什么；如果已足够，也写明“已足够”。

### 第 3 遍：可读性扫描 —— 函数内部好不好读

这一遍只看函数 / 方法 / 脚本内部的阅读体验，重点检查“入口注释之外”的复杂处、易混处和关键处。

对清单中的每个代码文件，检查是否存在以下需要内部注释的位置：

- **多步骤流程**：一个函数内连续完成 3 个以上步骤，例如读取配置 → 查询数据库 → 转换结果 → 组装响应。
- **复杂分支**：`if/elif/else`、异常兜底、早返回、权限分流、安全拦截等会影响行为走向的地方。
- **新手不直观的技术点**：例如 SQLAlchemy 查询、Alembic metadata、sqlglot AST、Pydantic Schema、FastAPI 依赖注入、TestClient 依赖覆盖等。
- **数据结构转换**：例如 ORM 对象 → Pydantic、RowMapping → dict、Decimal/datetime → JSON、YAML → 内部对象等。
- **安全 / 权限 / 校验逻辑**：例如 SQL Guard、敏感字段、RBAC、参数校验、危险操作拦截。
- **关键业务口径**：例如 GMV、退款率、时间窗口、固定业务事实、评测标准答案等。
- **容易踩坑处**：例如 循环导入、测试库和主库差异、MySQL / SQLite 方言差异、连接生命周期、trace_id 透传。
- **兜底检查**：连续 20-30 行核心逻辑：不含纯 import / 常量定义 / 装饰器堆叠。如果完全没有注释，必须补步骤注释或关键行注释。
- **注释有可能过时：**新增文件不需要担心这个问题，但如果是在已有文件的代码上进行了修改，那么之前原有的注释可能会过时，需要更新

判断标准：

- 如果读者只看函数开头注释，仍然看不懂中间某段为什么这样写，就需要补内部注释。
- 内部注释优先解释“为什么”和“这里在防什么坑”。
- 长函数优先使用步骤注释，并加上分隔线，例如：`# 步骤 1：XXXXX ==========` 和 `# 步骤 1-3：XXXXX ----------`
- 短但关键的逻辑用 `# ★ ...` 点明原因即可。
- 一个文件里的主角函数也需要在docstring添加 ★ 标注。
- 如果某段代码已经通过命名、结构和上下文足够清楚，不要为了凑数量硬加注释。

产出：

- 列出检查到的内部复杂点，以及是否补了注释。
- 示例：`app/api/query.py：为 SQL Guard 拦截分支、RowMapping 序列化、未命中模板路径补充内部注释。`

### 第 4 遍：形式扫描 —— 格式好不好看

这一遍只看形式，不看内容深度：

- **对齐线**：检查 `# 步骤 1：XXXXX` 或 `# 步骤 1-3：XXXXX` 是否有分割线，以及分割线长度是否达标，`==========` / `----------` 分隔线补齐到每行总宽约 100 列（中文按 2 列计），同文件内大致视觉对齐，目测即可。
- ★ 标记密度：关键点是否有 ★，普通流程说明不要滥用；如果同一文件里 ★ 太多导致重点失焦，需要精简。
- **语言**：注释是否以中文为主。大面积英文且无中文解释的，补中文。
- 产出：列出改了哪些文件的格式，如 `app/api/query.py：补 2 处分隔线对齐 + 1 处 ★`。

### 收尾

4 遍扫描完成后，整理阶段 1 小结：

- 补写了几个缺失注释（第 1 遍）
- 深化了几个新概念/设计决策的解释（第 2 遍）
- 修了几处内部注释（第 3 遍）
- 修了几处格式（第 4 遍）

小结素材会随阶段 3 固化到 `<module>-notes.md`，供 `finish-docs` 写档案时使用，避免凭记忆总结。

## 阶段 2：运行验证

1. 先读当前阶段计划文件中本模块的「验证」或「验收标准」小节，确认是否有模块特定的验证步骤（如 eval 脚本、smoke 测试）。有则优先执行；没有则只跑通用命令。
   
2. 通用验证命令（以 CLAUDE.md 指定的项目 Python 路径为准）：

   Windows / PowerShell 常用：

   ```powershell
   $env:PYTHONDONTWRITEBYTECODE='1'
   # 测试（所有模块）
   <项目 Python> -m pytest -p no:cacheprovider

   # 数据库迁移检查（涉及 ORM / Alembic 时）
   <项目 Python> -m alembic check
   <项目 Python> -m alembic current

   # seed 数据完整性（涉及 seed 时）
   <项目 Python> -m scripts.seed_data --reset
   ```

   macOS / Linux 可用：

   ```bash
   PYTHONDONTWRITEBYTECODE=1 "<项目 Python>" -m pytest -p no:cacheprovider
   PYTHONDONTWRITEBYTECODE=1 "<项目 Python>" -m alembic check
   PYTHONDONTWRITEBYTECODE=1 "<项目 Python>" -m alembic current
   PYTHONDONTWRITEBYTECODE=1 "<项目 Python>" -m scripts.seed_data --reset
   ```

3. 记录要求：

- 记录命令是否成功
- 记录关键输出结论
- 有 warning 要说明是否影响本模块
- 命令失败时，不要掩盖；写明失败原因和是否阻塞

## 阶段 3：素材固化（本 skill 的收尾，也是 finish-docs 的输入）

把本模块收工所需的全部素材写入 `docs/notes/<module>-notes.md`（文件已存在则更新追加）。**这一步是硬要求**：`finish-docs` 写 AI_CONTEXT / dev-log 时只读 notes.md + git diff + 现有文档，不依赖本对话的记忆——所以素材不落盘，后半程就会写"过程细节未记录"。

notes.md 必须包含以下小节：

- **模块名称与改动文件清单**：模块名、`git diff --name-only` 归并后的文件范围
- **关键决策与取舍**：决策内容、决策原因、当时给出的选项、主要风险、推荐方案、用户最终选择（如果曾向用户确认过）
- **阶段 1 注释小结**：补了几处缺失注释、深化了哪些新概念/设计决策、修了几处内部注释、改了几处格式
- **阶段 2 验证快照**：每条命令的结论（数字、输出要点）、warning 是否影响、失败原因与是否阻塞；不能只写"验证通过"
- **参考资料**：查了什么，借鉴了什么，没照搬什么；未查阅写"无"
- **Handoff（下一模块交接）**：必须按照下方模板记录本模块已经交付且后续可以依赖的能力、下一模块建议入口、仍未完成或未证明的事项、需要延续的决策和边界、尚未触发的决策门，以及下一轮规划必须读取的精确文件或章节。本小节只负责交接事实，不负责提前制定下一模块。

如果某个素材确实缺失（开发时没有记录），在 notes.md 里明确写"过程细节未记录"，不要脑补。

## 收尾

最后回复用户，列出本次整理做了什么：

- 补了哪些注释（阶段 1 小结）
- 跑了哪些验证及其结论（阶段 2 快照）
- 素材固化到哪个 notes.md（阶段 3）
- Handoff 是否已完整写入 notes，以及下一模块建议从什么问题开始

如果本次模块任务还未写 `dev-log.md / AI_CONTEXT.md / AI_CONTEXT_CHANGELOG.md`，重新读取 `finish-docs` skill 全文，然后继续执行。
